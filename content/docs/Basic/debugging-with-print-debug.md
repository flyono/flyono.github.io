## 引言：为什么调试技术对游戏开发至关重要

在游戏开发中，漏洞是无法避免的。识别并修复导致玩家行为导致意外结果或游戏崩溃**的原因——调试** ——显著影响开发流程的质量和效率。

许多初学者倾向于依赖 `print（）`函数作为最便捷的调试方法。然而，随着项目规模扩大，这种方法很快就达到极限。

- **日志洪流** ：主机被大量日志淹没，丢失了真正重要的信息。
- **大规模重做** ：调试后需要删除大量 `print（）`语句，且经常有遗漏的风险。
- **性能问题** ：`print()`语句留在发布中会略微影响性能。

本文解释了通过战略性地利用 Godot 引擎内置强大的调试工具，尤其是 **`print_debug（）`**函数，更高效地修复错误的具体方法。

## 在日志输出之间选择：`print` 、`print_debug`还是 `push_error`

Godot 有多种方式输出消息，每种方式都有相应的角色。 正确使用这些是清理调试的第一步。

| - | 调试执行 | 发布构建 | 主要用途 |
| ---------------- | ------ | ------ | ----------------------- |
| `print()` | 输出 | 输出 | 开发过程中非常临时的测试。不应留在生产代码中。 |
| `print_debug()` | 输出 | 通常不会输出 | 开发/测试期间的临时信息检查。 |
| `push_warning()` | 作为警告输出 | 通常不会输出 | 非致命但意外状态或已弃用的使用情况。 |
| `push_error()` | 错误输出 | 通常不会输出 | 在程序继续变得困难的明显错误状态时，及时通知。 |

*行为可能因构建设置和执行环境而异。* **对于绝对不能出现在生产环境中的日志，明确使用 `if OS.is_debug_build():`**

由于 `print_debug()`基本上只在调试构建中输出，开发者可以更方便地将调试信息嵌入代码中。此外，在调试器的"错误"标签页中使用 `push_warning()`或 `push_error()`记录输出，并带有可追溯的堆栈痕迹，便于识别问题源。

```gdscript
func load_level(level_id: int):
    if level_id < 0:
        # Warn about unexpected value
        push_warning("Invalid level ID passed: %d" % level_id)
        return

    print_debug("Starting load of level %d." % level_id)
    # ... loading process
```

## 精通 Godot 调试器：实时审视代码

Godot 调试器不仅仅是日志查看器。它提供了强大的工具，用于暂停游戏执行和详细调查内部状态。

### 1. 断点与步骤执行

**断点**是最基础且最强大的调试功能。只需在脚本编辑器中点击行号左侧，游戏执行就会在到达该行时停止。

执行暂停时，可以执行以下操作：

- **Step Over （`F10`）：** 执行当前行并进入下一个。如果有函数调用，你不会进入该函数的内部结构。
- **Step In（`F11`）：** 执行当前的行。如果有函数调用，你输入该函数的内部结构。
- **Step Out（`Shift+F11`）：** 将当前功能执行到最后，呼叫者之后返回下一行。
- **变量监控（变量）：** 在左下角的"调试器"面板中，您可以检查当前作用域内所有变量的值。无需再写无数 `print()`语句。

### 2. 远程检查器：实施操控运行场景

调试器面板的"远程"标签页会显示运行中的游戏场景树。这支持以下操作：

- **实时属性编辑** ：选择节点并通过检查器实时修改属性（位置、颜色、自定义变量等）。非常适合界面微调或立即看到物理参数变化的结果。
- **动态节点创建/删除** ：在场景树中添加或删除节点以测试它们的效果。

### 3. 分析器和监控器：识别性能瓶颈

当游戏运行缓慢或帧率不稳定时，**"分析器"** 就派上用场了。启动性能分析器并运行游戏，即可测量每个函数的执行时间和调用次数（以毫秒为单位）。这样就能立即看出"哪个进程占用资源最多"，从而可以进行精准的优化。

**"监控"** 选项卡还提供 FPS、内存使用情况、场景中的对象数量等的实时图表，有助于了解整体性能状况。

## 实用代码示例：断言和自定义可视化调试

除了 `print`和调试器之外，让我们来看看更高级的技术。

### 使用 `assert`进行基于契约的调试

`assert`语句描述了程序的"契约"——"这个条件必须绝对为真"。当调试执行期间条件变为假时，程序会立即停止并报告错误。这有助于更早地找到错误根源。

```gdscript
# 操控玩家生命值的函数
func set_health(new_health: int):
    # 生命值必须大于等于0的断言
    assert(new_health >= 0, "Attempted to set negative HP value: %d" % new_health)

    health = new_health
    print_debug("Player HP updated to %d." % health)
```

如果 `new_health`接收到负值，这段代码在调试执行期间会立即停止并报错。在发布版本中， `assert`语句会被忽略，因此不会影响性能。

### 使用 `_draw`进行自定义可视化调试

敌方 AI 的探测范围、导航路径、物理力矢量——这些信息如果以数字形式记录，很难直观理解。使用 `_draw()`函数，您可以直接在游戏屏幕上绘制调试信息。

```gdscript
# 敌方角色脚本
extends CharacterBody2D

@export var vision_radius: float = 200.0
var can_see_player: bool = false

# 启用调试绘制的标志
@export var enable_debug_draw: bool = true

func _process(delta):
    var new_can_see = check_player_visibility()
    # 仅在状态发生变化时请求重绘
    if new_can_see != can_see_player:
        can_see_player = new_can_see
        queue_redraw()  # 需要再次调用_draw()

func check_player_visibility() -> bool:
    # 检测是否看见玩家的逻辑……
    return false

func _draw():
    if not enable_debug_draw:
        return

    # 绘制圆形检测范围
    var circle_color = Color.RED if can_see_player else Color.GREEN
    draw_circle(Vector2.ZERO, vision_radius, circle_color.lighten(0.5))
```

>**重要提示** ： `_draw()`函数并非每帧都会自动调用。要更新绘制内容，需要调用 `queue_redraw()`来请求重绘。

当启用调试 `true` `enable_debug_draw`时，附加了此脚本的节点会在屏幕上以圆圈的形式绘制其检测范围。颜色会根据玩家是否被识别而变化，从而使 AI 行为一目了然。

## 常见错误和最佳实践

为了高效调试，重要的是避免常见的反模式并养成最佳实践的习惯。

| 常见错误 | 最佳实践 |
| ----------------------- | ---------------------------------------------------- |
| 所有输出都使用`print()` | 使用**断点**进行复杂逻辑跟踪，使用 `print_debug()`进行状态转换检查——区分使用方法。 |
| 调试后注释掉 `print()`语句。 | 使用 `print_debug()`会自动在发布版本中禁用，因此无需注释掉。 |
| 凭借直觉优化性能。 | 在开始优化之前，使用**性能分析器**根据客观数据识别瓶颈 |
| 仅使用 `print()`追踪物理错误。 | 在调试菜单中启用"可见碰撞形状"，以**直观地确认**碰撞检测结果。 |
| 通过反复修改代码和重新执行来调整用户界面位置。 | 使用**远程检查器**在执行过程中直接调整 `position`和 `size`属性，并查看结果。 |

## 总结：建立高效的调试流程

在 Godot 引擎中进行高效调试，首先要超越仅仅使用 `print()`，并结合以下工具和技巧。

1. **充分利用 Godot 调试器** ：对于复杂的错误和逻辑跟踪，积极使用断点、单步执行和远程检查器——养成"窥探"代码内部状态的习惯。
2. **`print_debug()`的策略性使用** ：在开发过程中，为了跟踪状态和检查临时值，可以使用 `print_debug()`，它不会影响发布版本，从而保持代码库的整洁。
3. **通过性能分析器进行优化** ：当出现性能问题时，使用性能分析器来识别瓶颈并缩小调试范围。

掌握这些技巧，可以显著减少修复漏洞的时间，并将更多时间投入
到游戏的创意方面。
