> 制作 RPG 或动作游戏时，你总会遇到角色批量生产的问题。基础史莱姆已经完成。但随着你完善关卡，开始想要高血量史莱姆、双攻红色史莱姆、稀有掉落金属史莱姆等等。

最诱人的第一反应是复制 `Slime.tscn` 并逐个调整数值，但这很快就会崩溃。当你决定“所有史莱姆都应该移动得更快”的那天，你将不得不打开每个复制的场景进行修改。本文将介绍优雅的解决方案：场景继承、可编辑子节点以及适用于大型项目的数据驱动资源，以及何时使用每种方法。

## 场景继承: 从模版派生

场景继承将面向对象的类继承思想引入了 Godot 的场景中。您将一个现有场景作为父场景，并创建继承其所有结构和功能的子场景。如果您关心可重用性和可维护性，这是首选的方案。

继承有两个优势:

- 只需管理差异: 在子场景中, 可以自由的覆盖从父场景继承的属性(属性, @export 变量). 更改项在检查器中会显示 "重置" 图标.
- 父场景的更改会自动传递给子场景: 这是最大的优势。在父场景中添加一个补丁或新功能，更改会自动传播到每个子场景。“对所有角色统一修复”和“每个角色单独调优”可以同时实现。

这与复制粘贴截然不同。粘贴的副本已经与原版断开了联系，因此后续的共享修复意味着需要手动编辑每一个。

## 实践: 从 BaseEnemy 生成敌人变体

在一个 RPG 中变色的小怪，在一个动作游戏中增强的杂兵，在一个射击游戏中具有不同子弹类型的敌人: "一个共享基础加上每种类型的差异"正是场景继承的作用。让我们来构建它。

首先，创建 `BaseEnemy.tscn` 作为所有敌人的基础，并附加一个共用脚本。关键技巧是将数值设置为 **@export**, 这样子节点和检查器面板就可以对其进行调整。

```gdscript
# base_enemy.gd
extends CharacterBody2D

# @export lets inheriting scenes override it individually
# @export 允许继承场景对其进行单独重写
@export var health: int = 100     
@export var attack_power: int = 10
@export var speed: float = 50.0

func take_damage(amount: int) -> void:
    health -= amount
    if health <= 0:
        die()

func die() -> void:
    queue_free()                  # Shared death handling (reused by every enemy)
```

接下来，在文件系统面板中右键点击 `BaseEnemy.tscn` ，选择“新建继承场景”来创建 `StrongEnemy.tscn`。此时该场景的外观与行为和父场景完全一致。只需在检查器中将 `health` 改为250，`attack_power` 改为25，无需编写一行代码，这个强化版本就制作完成了。

当然还可以通过自己的脚本扩展父类的功能. 在覆盖父类方法的同时，可以通过 `super` 调用父类的实现。

```gdscript
# strong_enemy.gd
extends "res://base_enemy.gd"

func die() -> void:
    print("The mighty foe lets out a dying roar!")   # Extra flourish for this enemy only
    super.die()                                      # Also run the parent's die() (queue_free, etc.)
```

有两个值得注意的点。

- `BaseEnemy` 中的共享逻辑，子类中存在差异: 共享的移动和伤害逻辑位于一处，在 `BaseEnemy`, 子类仅包含"不同之处"。因此，当你后来需要为每个敌人修复移动时，一个 BaseEnemy中的修复即可影响所有变体。
- 使用 `super` 基于父类构建: 你无需完全重写 die()，只需添加额外的修饰并重用父类的清理功能 super.die()。你扩展而不破坏父类的行为。

> 警告: `queue_free()` 会在下一帧删除节点。继续引用已删除的节点会导致空引用错误。当其他节点持有引用时，养成使用 is_instance_valid()检查有效性或通过 `NOTIFICATION_PREDELETE` 清理的习惯。

## 子节点可编辑: 仅更改这一个实例

如果场景继承是为了"创建可重用的模板"，那么可编辑子项就是为了"现场调整一个特定的放置实例"。它允许你在不创建新场景文件的情况下编辑实例化子场景的内部节点。

它适用于此类一次性调整

- 仅对 Boss 房间中的单个哥布林将手臂 CollisionShape2D放大以扩大其攻击范围
- 仅将第一个教程敌人中的 speed设置为 0 使其不移动

这样做很容易。右键单击主场景中放置的实例并勾选"子节点可编辑"，其内部节点将在树状结构中展开，可以直接选择和编辑。

话虽如此，该更改仅适用于当前实例，无法重复使用。如果你觉得“我之后可能还会用到这个”，标准操作是右键单击并选择“将分支另存为场景”，将其升级为继承场景。

## 在二者之间做出选择，以及数据驱动型资源

这三种方法是根据目的选择的。

- **场景继承**: 根据类型变化节点结构或视觉效果的变体。默认策略。
- **可编辑子节点**: 一个单例的例外。一次性的调整。
- **数据驱动资源**: 许多变化仅数字不同。

在特定于拥有数百种怪物类型的 RPG 规模上，仅靠场景继承会让你管理过多的场景文件。这时，"数据驱动设计"，即将角色参数分离到 `Resource`中，就能发挥优势。

给 `BaseEnemy.tscn` 一个 `@export var data: CharacterData`, 并替换成 `slime_data.tres` 或 `dragon_data.tres`, 你就可以表达数百种敌人类型，同时只使用一个场景。参数调整完全在 `.tres` 文件中进行。详情请参阅 "创建和使用自定义资源"。

"不同的视觉效果和结构意味着继承，不同的数量仅意味着数据驱动，"而将两者结合（将数据资源插入继承的场景）是实际的应用点。

## 常见错误和最佳实践

| 常见错误 | 最佳实践 |
| --- | --- |
| 使用可编辑子项处理所有内容 | 只要有可能重用，就选择场景继承。如果你觉得“我以后可能会用到这个”，就把它做成一个继承的场景 |
| 过度嵌套继承 | 将继承限制在两个或三个层级。超过这个范围，考虑使用组合或数据驱动的方法 |
| 父级场景假设子级状态的情况 | 保持父级自包含并提供通用功能。具体行为是子级的决定 |
| 仅仅为了改变一个数字而添加脚本 | 将生命值、攻击力和速度 `@export` 设置为可编辑，以便设计师可以在检查器中安全地调整它们 |

## 小贴士

- **组合优于继承**: 这是面向对象编程的经典建议。与其使用深度继承，将功能作为子节点添加（即"组合"）在 Godot 中通常更灵活。当继承开始显得限制性时，将"攻击组件"和"生命值组件"结合起来就是你的下一步行动。
- **运行时性能不是问题**: 场景继承和可编辑子项最终都会被解释为一个场景树，因此没有实质性的运行时差异。根据可维护性来选择。
- **继承的场景不能删除节点**: 来自父节点的节点不能被子节点删除。如果不需要，关闭其可见性或调用 `queue_free()`。

## 总结

- 场景继承是通过仅更改差异来从模板派生变体的标准方法。父级更改会自动传播到每个子级
- 在子脚本中使用 super可以扩展同时保留父级的行为
- **可编辑子节点**是针对现场调整单个放置实例的例外路径。它不能被重用
- 使用数据驱动的资源（每种类型一个场景加一个 .tres）更容易管理大量变化
- 选择: "不同的结构意味着继承"、"不同的数量仅意味着数据驱动"、"只有一个实例意味着可编辑子项"

首先创建一个 `BaseEnemy` 并在一个继承的场景中重写 `health`。当你体会到“修复父级就能修复一切”的感觉时，批量生产的设计就会变得容易得多。
